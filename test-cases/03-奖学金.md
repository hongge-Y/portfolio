# 03 · 奖学金多级评定（SCH）

两条状态机（`docs/01-需求规格说明书.md` §4.3）：

```
计划：草稿(0) → 报名中(1) → 评审中(2) → 公示中(3) → 已结束(4)
申请：10待审 → 20辅导员通过 → 30院系通过 → 40通过 → 60公示 → 70发放
                    └──── 驳回 ────► 50已驳回
```

计分：`total = gpa*10*0.6 + 红榜加分 − 黑榜扣分 + 综合素质分`（规则来自 `sch_plan.rule_json`）；并列按 `gpa` 降序、`create_time` 升序。

**执行入口：`bash scripts/smoke-scholarship.sh`**（16 条断言，四级流转 + 越级拦截 + 排名 + 公示 + 发放全链路）。

| 编号 | 前置 | 步骤 | 预期 | 依据 | 状态 |
|---|---|---|---|---|---|
| TC-SCH-01 | 管理员 | `POST /scholarship/plan` 建计划（未到报名期）→ `GET /scholarship/plan/available` | 学生端不可见；直接 `POST /scholarship/apply` 返回 `code=400 SCH_PLAN_CLOSED` | I1/I5 / 7.5 | 已设计 |

| TC-SCH-04 | 书记 | 直接审批状态 10 的申请（越级，跳过辅导员） | 被拒，申请状态不变 | I11 / 状态机 | 脚本覆盖 |
| TC-SCH-05 | 辅导员 | `POST /scholarship/approve/search` | 待办含该申请 | I10 | 脚本覆盖 |

## 观察项

- **公示期校验在接口层还是查询层**：TC-SCH-11 的拒绝点要确认是"发放接口自己判公示结束时间"，还是只靠管理员不点——如果是后者，属于防呆缺失（前端藏按钮 ≠ 后端拒绝），这也是 `docs/01` §2.1 那句"权限与规则一律后端判定"的落地检查点。
- **排名与公示的一致性**：TC-SCH-09 生成的榜单和 TC-SCH-10 的公示名单必须是同一份数据。脚本里是"排名已生成 → 公示名单含该学生"两步断言，足够；但并列名次的排序规则（gpa → create_time）还没被断言覆盖，属于**用例缺口**，需要手工造两个同分样本验一次。
